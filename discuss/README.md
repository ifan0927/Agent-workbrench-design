# 分題訪談與設計交接

建立日期：2026-09-11。

目的：用短而聚焦的問答釐清 user journey 與 agent 工作方式，直接把可接手的結果保存在 repo，不靠使用者跨 session 複製對話。訪談可以用偏重互動速度的設定，跨主題一致性與正式系統設計另行統整；不以模型名稱判定紀錄是否可信。

本入口採用使用者本輪要求的「分題、短訪談、固定位置回報」。下列主題切分與節奏是起始做法，可依實際訪談調整，不是首版功能承諾或必須完成的九場關卡。Harness 外層的共用指引、專案 AGENTS.md、模式、skills、context 與流程政策須與 journey 一起釐清，不能只訪談 UI 功能；其正式產品與技術邊界仍由後續統整落到 docs。

## 文件責任

- `discuss/{topic}/README.md`：每個主題唯一的訪談紀錄，依 [模板](_template.md)建立；同主題可以分多場接續，不為每輪或每個 session 建新檔。
- [prompts.md](prompts.md)：訪談與統整的啟動指令。
- [product.md](../docs/product.md) 與 [design/](../docs/design/README.md)：正式產品／設計文件；已確認、候選、待驗證等身分仍依各文件及條目判讀，不把整個 docs 當成全部定案。
- [lab/](../lab/README.md)：既有實驗程式與結果；訪談不改寫歷史驗證結果，也不自行追加執行。

`discuss` 保存意圖、例子、取捨與待決事項，不建立另一份完整架構文件。訪談中的明確回答不等於已完成跨主題整合，也不自動授權實作。與現行文件不同的新要求保留為「更新意圖／待整合」，不隱藏衝突。

## 每場如何訪談

1. 讀根目錄 AGENTS.md、本入口、當前主題紀錄與真正相關的正式文件。已有答案不重問，不掃完整 docs／lab。已提供的內容足夠時不再重抓同一檔案。
2. 用簡短文字說明本场只釐清的片段及已有基準，直接提出第一個最有價值的問題；不要先列完整問卷或整體架構。
3. 每輪只問一個主要問題。先請使用者描述具體工作，再追問必要反例、邊界或取捨；允許開放答案、其他選項、不知道及延後決定。
4. Grill 的意思是指出含糊、矛盾與隱藏代價，不是辯論、誘導同意或持續追問。可以協助想例子、提供少量中性選項，但必須區分使用者需求與 AI 的方案。
5. 預設約 5–8 個有效問答就收斂一個小片段；這是節奏建議，不是題數配額。答案充分就提早結束，沒完成也可保存接續，不為補齊表格而繼續問。
6. 一般回覆只包含必要的理解確認、至多一個具體追問。只有收斂時才產生較完整摘要，不在每輪寫長篇設計。使用者說「換題」「先存」「今天到這裡」時停止擴問並保存。

正常、必要例外與不得發生的事需要被看見，但不要求窮舉所有失敗或畫面。技術不確定性記成研究問題；不要把訪談變成框架 survey 或當場實驗。

## 固定回報與接續

回報格式見 [_template.md](_template.md)。必要內容是範圍、已有基準、使用者明確表達、具體 journey／行為案例、候選與未知，以及下一次從哪個問題開始。

每次取得一組有意義的結論、使用者要求保存或本場結束時，依當次授權更新該主題檔。可先保存未經總結確認的摘要，但必須標記；不得把使用者沉默、訪談結束或 git commit 當作確認。

條目可用 `U01`、`J01`、`O01` 等簡短穩定 ID，引用時加主題代號。使用者明確回答保留簡短轉述、必要的短原話與日期；AI 推導另列。沒有可用的對話連結時不虛構。不保存逐字稿、私人帳號細節、企業資料、憑證或完整本機紀錄；本 repo 在建立本入口時為公開。

主題狀態只在該主題檔維護，不另外在入口複製動態狀態表：

- 訪談進度：`in-progress` 或 `ready-for-synthesis`。後者表示有足夠材料供統整，不代表答案全有或設計已批准。
- 摘要確認：記錄哪些條目已明確確認、哪些只是尚待確認的整理。
- 整合追蹤：以來源 commit、已處理條目、目標文件與仍待處理事項記錄；不以單一 integrated 標記吞掉未決問題。後續新答覆是待重新核對的增量，不因先前已整合就自動採纳。

## 寫入範圍與版本安全

本入口本身不是寫入授權；由使用者的啟動指令指定 repo、分支與範圍。標準訪談指令授權只新增／更新當前 `discuss/{topic}/README.md`，不修改正式 docs、其他主題、其他 repo、程式、憑證或執行實驗。

先使用當前可用 GitHub 工具實際讀取。寫入前重新取得目標檔的最新內容與 blob SHA；不存在時建立，存在時以最新 SHA 更新，保留其他 session 的變更。衝突時重新讀取並核對，不能以舊全文覆蓋或 force push。不同主題可在不同 session 進行；同一主題避免同時修改，並行結果的語意衝突留給統整。

沒有檔案寫入工具或被分支規則拒絕時，先保存可保留的本地草稿／在對話說明未同步，回報具體限制；不得因帳號 metadata 顯示 push 權限就宣稱已寫入，也不能擅自改走另一個 repo 或分支。只有工具回報成功並讀回核對後，才回報路徑、commit 與狀態。所有保存均在當前互動實際完成，不承諾離開後自動寫回。

## 統整與正式設計

統整指令見 [prompts.md](prompts.md)。統整者先讀指定主題及其來源，再按影響範圍核對 product／configuration／workflow／architecture，不依賴記住前一個聊天。

只將使用者明確表達且不衝突的內容整理為產品基準；未確認的轉述、AI 方案、技術候選與衝突各自保留原身分。確有衝突時指出來源、可先進行的部分與最少必要決定，不默默選邊，也不重新問整份訪談。

正式結論回到既有主題 docs，訪談檔只補條目到文件的追蹤與未決事項。統整不生成另一份巨大的 summary／master-spec，不把全部訪談完成當成系統設計前置條件，也不因落檔就授權產品實作或模型實驗。
