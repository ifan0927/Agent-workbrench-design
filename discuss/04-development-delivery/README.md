## 1. 範圍與既有基準

本場只談一般開發的自主完成範圍、必要打斷、可開始檢閱的成果與接手材料。交付形式若影響體驗可以討論，但不預設 PR、commit、報告或特定 UI。本場不談複雜失敗恢復、取消、並行衝突、session／容器生命週期或完整合併／部署／發布流程。

沿用基準：

- Project onboarding 已通過，目標、重要方案與限制已清楚，使用者已确认開始開發。見 [product：專案入場與 onboarding、單次目標釐清與階段銜接](../../docs/product.md)。
- 重要取捨與純實作細節分開；已選方案內的細節由 agent 在授權範圍依 repo 慣例處理。改變外部行為、範圍、風險或重要維護方向時，沿用必要取捨基準。見 [workflow：目標釐清與必要取捨](../../docs/design/workflow.md#目標釐清與必要取捨)。
- 索引提供方向，模型逐層按需閱讀；是否需要研究及何時足夠由模型自主判斷，使用者可追加方向。研究接手保留已探索方向、repo 內已讀內容及重點結果。見 [product：產品假設](../../docs/product.md#產品假設)及 [workflow：研究交付或等待回答](../../docs/design/workflow.md#研究交付或等待回答)；索引細則本場直接沿用啟動指令，不另展開。
- 研究允許保留的實作待驗證事項，不代表開發交付時已驗證，也不免除既定要求。見 [workflow：研究交付或等待回答](../../docs/design/workflow.md#研究交付或等待回答)。
- 執行結束、成果達標、使用者採納與下一步授權分開。現行「開發 → 驗證 → fresh review → 有限修正」及修正輪數仍為候選；需要 review 不等於已決定另一個 agent。見 [workflow：開發與 review 的候選契約、開發、review 與有限修正](../../docs/design/workflow.md)。
- 合併、部署與維運不自動納入交付。見 [product：明確不納入](../../docs/product.md#明確不納入)。
