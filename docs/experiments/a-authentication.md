# A．認證與平行執行：優先驗證

狀態：已在 [lab/A](../../lab/A/README.md) 實作並執行部分真實與模擬驗證；逐項結論與未驗證範圍以[驗證結果](../../lab/A/RESULTS.md)為準。整理日期：2026-09-10。

[實驗入口與執行前提](README.md) · [相關候選設計](../design/authentication.md)

| ID | 驗證問題 | 最小做法 | 通過條件／設計影響 |
| --- | --- | --- | --- |
| A1 | 短效 token 注入能否工作？ | 平台取得認證，啟動一個容器，透過 app-server 登入並完成小任務。 | 確認預期帳號與認證模式；容器不需要 refresh token。失敗會影響接入選型。 |
| A2 | 能否真正平行執行？ | 兩個容器各用獨立工作目錄、配置與 session，同時完成不同任務。 | 執行時間確實重疊，結果不串到另一工作；不能只確認容器都已啟動。 |
| A3 | 同時要求刷新如何處理？ | 先模擬兩個 worker 同時要求更新，再另驗證真實刷新。 | 同一份認證只進行一次刷新，其餘沿用更新結果；不把整段工作序列化。 |
| A4 | 刷新途中平台中斷會如何？ | 模擬刷新前、遠端已刷新但本地未保存、已保存但尚未回覆三個中斷點。 | 辨識可接續與認證狀態不明；後者允許要求重新登入，不盲目重送舊 refresh token。 |
| A5 | 撤銷、逾時、額度耗盡如何呈現？ | 用固定錯誤回應模擬，不撤銷日常認證、不故意耗盡訂閱。 | 分清重新登入、暫停等待、額度不足；不自動切換 API，不無限重試。 |
| A6 | 是否污染日常登入或洩漏認證？ | 檢查認證來源與寫入位置；以假 token 檢查日誌、checkpoint、成果及程序參數。 | 不覆寫桌面／CLI 日常認證；秘密不混入一般工作紀錄。 |

證據限制：A3 的模擬成功只證明刷新協調邏輯；真實 OAuth 刷新須另留證據。短時間兩個 worker 都成功，也不能替代刷新測試。短效 token 仍代表帳號存取權，不是平台自行簽發的工作專屬權限；平行工作仍共用帳號額度。
