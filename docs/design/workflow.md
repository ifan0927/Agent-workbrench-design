# 工作生命週期與成果交接

狀態：混合已確認行為基準與必要語意的候選設計；各節分別標示，不是完整 API／DB schema。整理日期：2026-09-11。

平台保存工作意圖、有效配置、結果及人的決定；Codex 處理工作內的探索與修正。執行結束、成果達標、使用者採納及下一步授權必須分開。

## 身分與 context

| 概念 | 語意 |
| --- | --- |
| 工作項目 | 使用者持續下目標、留言、回答與檢閱成果的單位。 |
| 已授權工作段落 | 一次明確開始或接續的範圍；可包含開發、驗證、review 與有限修正。 |
| Run attempt | 一次可辨識的執行嘗試；重送同一派發不應自行建立新身分。 |
| Codex session／thread | 一段連續上下文；使用明確 ID，不以「最近一次」推定。 |
| 容器 | 可拋棄執行資源，不是工作或 session 的永久身分。 |

普通留言先保存、不必立即啟動 agent，仍是一般留言的候選處理方式；必要問題的回覆已依[回答接續基準](#必要問題的回答接續)明確為回覆後接續，不能再要求額外開始操作。一般模糊留言的判讀未另定規則。明確開始、要求修改等操作的具體輸入契約仍待設計。

同一段工作盡量延續 context，不每次工具呼叫重開 session；這是候選接手方式。回原工作提出 PR 修改的偏好，不等於指定同一 agent、session 或容器；獨立 review 的角色要求見[下節](#code-工作的獨立-review)，其 context 配置尚未定案。

保留且相容的 session 可 resume；否則依保存的成果與限制建立新 context，是一般候選接手方式，不承諾昂貴 session 遷移或原程序復活。Clarification 的正常等待與手動中斷須符合下節已確認的連續性需求，不能只因一次回合結束就套用重建。

### Clarification 的連續性

已確認需求，來源：[02-clarification](../../discuss/02-clarification/README.md) U03–U05：多輪問答必須能延續先前探索結果；clarification 尚未完成時，原 session 原則上不回收。使用者應能透過 bench 手動觸發中斷。等待回答與單一回合完成，不等於使用者中斷。

手動中斷後恢復完整工作脈絡是 nice-to-have；若成本或狀態管理複雜度過高，使用者接受脈絡終止。此限定只適用手動中斷，不延伸成正常等待時可以丟失脈絡，也不授權刪除已交付成果。

Session 保存成本、期限與異常失效處理尚待查核。Session、app-server 程序與容器是否需一起存活尚未選定；為新增能力重啟環境／session 只是候選，須另核對連續性，不把它當成 U04 的已確認例外。

### 必要問題的回答接續

已確認行為，來源：[05-interaction-recovery](../../discuss/05-interaction-recovery/README.md) U01–U04。Agent 在已授權工作內提出必要問題並等待時，使用者想好答案後直接回覆，agent 就接著做，不需額外啟動。問題應交代目前難點等有助作答的背景，具體資訊由模型自主判斷，不訂必填欄位清單。

回覆後畫面能辨識 agent 正在處理、看得出其狀態即可；具體 UI、通知通道與狀態表示未定。不為「尚未想好先補資料」的反例增加流程。這些回答不將一般留言一律視為開發授權，也不改變重要取捨與階段銜接的既有分界。

### 工作內的探索接手

已確認目的，來源：05 U11——降低新一輪 agent 的探索成本；使用者目前未指定非保留不可的內容，不追加必填 handoff 清單。此目的不取消既有研究接手與成果保存要求。

使用者候選（05 U10）：在同一工作內提供共用暫存區，供流程中的 agent 讀取狀態訊息、handoff 等內容。是否採用、保存哪些內容、誰維護、期限與讀取方式尚未選定，也未承諾量化節省。它不是跨工作知識庫或 repo 全文副本。共享內容與 reviewer context 的關係留待設計，不因「可看共用區」就預設所有對話必須注入每個 agent。

## 目標釐清與必要取捨

以下為已確認行為，來源：[02-clarification](../../discuss/02-clarification/README.md) U01–U03、U06–U09。適用於 project 已通過 onboarding 的單次工作，不另建 project gate。

| 情境 | 預期 agent 行為與分界 |
| --- | --- |
| 使用者提出模糊目標 | 先釐清真正關心的目標，不自行挑一種解讀後以診斷取代釐清。可以讀 repo 了解背景；閱讀路徑與深度依 [索引規則](configuration.md#索引與閱讀自主性)按需判斷。 |
| 使用者自己也說不清楚問題 | 可以用初步 survey／診斷協助形成問題；這不等於採納某個實作方案。 |
| 方案會改變成果形狀且有重要 trade-off | 呈現方案與取捨，取得使用者選擇；即使低成本、可逆，也不足以直接自行採用。 |
| 面對上述方案，使用者回答「不知道／你決定」 | 先提出推薦與理由，再請使用者確認；此規則不擴大到所有純實作細節。 |
| 目標與方案已定，只剩實作細節 | 在已授權開發範圍內，命名、內部拆分、測試風格等依 repo 慣例自主處理；若改變外部行為、範圍、風險或重要維護方向，回到必要取捨。 |
| 需求探索已足以接續設計 | 可以繼續設計討論；設計進入開發須有使用者確認，方案採納與開發授權分開判斷。 |

### 接手內容的候選整理

以下是依訪談與既有通用結果契約形成的 AI 候選，尚未逐欄確認：保留目前目標與關注點、已確認方案（若有）及理由、範圍與限制、假設與未知、必要問題、證據引用及下一步授權。研究接手中已由 03 明確回答的內容另見[研究旅程](#研究交付或等待回答)；不據此將本段全部候選欄位視為已確認。它不是完整規格問卷，也不是所有欄位填滿才准繼續的 gate。尤其需求探索接續設計，不要求先完成實作方案比較；未回答問題及技術未知不自動轉成假設或採納。

## 依工作指引驗證與回報

已確認的跨專案行為要求，來源：[06-global-guidance](../../discuss/06-global-guidance/README.md) U03–U05；適用各類工作，不限 code。

| 情境 | 預期 agent 行為與分界 |
| --- | --- |
| 工作指引已有驗證要求 | 做完工作後，依適用的工作指引完成對應驗證。 |
| 工作指引未規定驗證方式 | 模型自行判斷並完成最低必要驗證；不另要求使用者列完整分類、固定步驟或證據門檻。 |
| 回報工作成果 | 說明實際使用的驗證方式；自行判斷的驗證也須回報。 |

使用者預期指引未規定的情況屬少數，是使用預期而非實測頻率。最低必要驗證的自主性僅補足未規定的情況，不取代既有驗證要求、不等於免驗證，也不授權開通服務或擴張工作範圍。指引已有要求但環境不能執行，不能直接當作「未規定」而降低要求；沿用既有能力缺口與受限驗證的分界，不在此新增處理流程。

回報方式是已確認內容要求，報告模板、固定欄位與完整 logs 則未指定；不因本節而將下方候選結果契約整段升格為已確認。主動探索依 [configuration](configuration.md#索引與閱讀自主性)，code 工作仍須[另一個 agent review](#code-工作的獨立-review)，不能用本節的自行驗證取代。具體指引配置與外層確保方式留 08／09，專案驗證入口及維護留 07。

## Issue 任務單與程式完成

已確認需求，來源：[04-development-delivery](../../discuss/04-development-delivery/README.md) U01–U02／J01。適用於需求／設計銜接已授權開發的工作，不改變各工作入口可獨立使用的基準。

| 階段／事件 | 已確認行為與界線 |
| --- | --- |
| 需求／設計討論產出開發任務 | 產出固定格式的 issue 任務單，作為後續 agent 開發的輸入；不是把「固定格式 issue」解讀成開發完成後的成果報告。 |
| 使用者確認開始開發 | Agent 依該 issue 完成程式工作；產出 issue 本身不替代開發授權。已選方案內的實作自主性與重要取捨沿用[既有基準](#目標釐清與必要取捨)。 |
| 判斷開發成果 | 以 issue 要求在程式上的完成為準；PR 通過、合併與使用者採納分開判斷，不以關閉 issue 的操作替代程式完成。 |

例如報表匯出改成背景處理：需求、重要方案與限制討論清楚後，以固定格式 issue 交接；取得開發授權後，agent 完成該 issue 的程式要求。這個案例沒有選定 issue 的承載平台，也沒有授權自動開 PR、關閉 issue、合併或部署。

固定格式的具體欄位、產單機制、issue 與平台工作項目的身分映射、程式完成的具體驗證及接手呈現尚未設計。本場未討論的內容不能推定為可略過：研究階段保留的實作待驗證事項仍需依既定要求處理；不能因 issue 格式完整或 agent 宣稱完成就視為已驗證。[依工作指引驗證與回報](#依工作指引驗證與回報)的行為要求已由 06 補入，但未固定具體方法。下節的 code 獨立 review 要求已由後續 05 訪談確認；結果契約、具體驗證／修正流程與修正輪數仍為候選或待決，不因 issue 任務單或 review 角色已明確就整段採納。

## Code 工作的獨立 review

已確認要求，來源：[05-interaction-recovery](../../discuss/05-interaction-recovery/README.md) U12–U13：所有 code 相關工作都要交給另一個 agent 做 review，不限 PR 後修改，不能以實作者自我檢查或程式測試取代。此需求補足 04 尚未決定的 review 角色，不改變 issue 的程式完成與 PR 通過／合併分開的基準。

另一個 agent 的 context／容器隔離、工具、review 範圍與結果格式，以及發現問題後的修正安排、輪數與交回人的條件，尚未設計；不將以下候選契約全部升格為已確認。非 code 工作是否需額外 review 不由此要求推定。

### PR 後修改與交付

已確認偏好與行為，來源：05 U06–U09、U12：

- 理想是在 GitHub review 後直接留言，交給 agent 修改；使用者也接受看完 code 後回平台留言，把所有要修改的內容放進去。兩種入口尚未選定，GitHub 整合的實作與維護難度需評估，不以過往工具經驗視為已證明複雜。
- 回平台時偏向在原本開發該 PR 的工作留言接續，不要求另開工作；此替代路徑不以 agent 自行收集 GitHub review 意見為必要輸入方式，也不禁止按需讀取 PR 背景。
- 修改完成並驗證、由另一個 agent review 後，直接更新原 PR，交給使用者再 review。這是已授權 PR 修改工作的交付預期，不延伸為所有工作自動建立 PR、合併或部署。

哪些 GitHub 留言形成修改要求、入口整合、輸入對應版本及具體發布機制仍待設計，不先加入自動監聽或設定固定修正輪數。

## 開發與 review 的候選契約

| 契約 | 必要內容 |
| --- | --- |
| Worker 輸入 | 工作／attempt 身分、目標與限制、有效配置、repo 基準、既有成果、完成條件、修正額度與發布授權。 |
| 通用結果 | 執行結果、摘要、產物位置、待回答問題、未完成事項、已知外部副作用。 |
| 開發結果 | 候選 commit、相對基準的變更、實際驗證與未驗證項目；未 push 時仍有可重建候選的資料。 |
| Review 輸入 | 固定候選、需求與規則、驗證紀錄；不承接開發對話，但可讀完整相關程式。 |
| Review 結果 | Findings、位置與依據、阻擋性、檢查限制；允許無法完成判斷。 |
| 人工決定 | 回答／採納對應的問題、需求版本與候選，以及是否授權下一步。 |

結構化格式只證明可解析，不代表語意正確或工作達標。候選改變，不能無條件沿用舊測試與 review 證據。

## 三條操作旅程

### 研究交付或等待回答

以下研究行為為已確認基準，來源：[03-research-design](../../discuss/03-research-design/README.md) U03、U05–U08／J01–J03；成果方向與開放考量面向見 [product](../product.md#研究與設計的成果方向)。適用於 project 已通過 onboarding、當次目標已清楚的工作。

| 情境 | 預期 agent 行為與分界 |
| --- | --- |
| 開始處理目標 | 先自主判斷是否需要研究，或通用解法已足夠，考慮研究的額外成本。使用者信任此判斷，只需指引，不要求另找證據證明這屬於通用常見問題。 |
| 需要研究與比較 | 有多人使用的開源專案、相關使用紀錄與經驗分享可提供有用依據；不限制格式，不預設來源配額、人氣門檻或必查工具清單。 |
| 已能提出推薦，仍可搜尋更多方案 | 是否繼續擴大、何時足夠可交付，由模型依任務自主判斷；使用者有需要時會提出額外方向。不另設研究停止的證明關卡。 |
| 交付後暫未選方案，後續由另一個 agent 接手 | 保留已探索方向、repo 內已讀內容與重點結果等，讓後續設計能利用已有探索材料。保存本身不代表選定方案。 |

操作旅程：固定本次輸入與配置 → worker 自主判斷並進行所需研究／設計 → 交付建議與接手材料。遇到必要產品取捨，保存具體問題與目前成果後等待；使用者回答才接續。是否研究與何時交付的自主性，不改變[重要取捨與開發授權](#目標釐清與必要取捨)的分界，推薦、採納及進入開發仍分開判斷。

既有保存來源、結論、未知與建議的方向繼續適用；03 U08 明確補入上述探索接手內容。具體格式、已讀內容如何表示與保存／載入機制尚未設計，不要求完整原文副本，也不禁止接手者按需重新閱讀。這些內容需求不將其他候選結果欄位一併升格為已確認 schema。

等待可以在工作回合邊界完成，但不等於回收 clarification session；連續性依[已確認需求](#clarification-的連續性)處理。是否支援 app-server 執行中問答另依接口驗證，不因接入 app-server 就擴張成完整即時聊天。

已認可的受限驗證案例（[02 U13／J05](../../discuss/02-clarification/README.md)）：討論查詢效能時，agent 已讀程式、schema 與測試，但沒有具代表性資料的測試資料庫。可以交付有依據的索引等候選、尚未驗證的效能假設及後續驗證方式，繼續設計討論；這是暫時足夠的進展，不代表效能已驗證、整份設計已採納或可開始開發。不能泛化為所有能力缺口或高風險未知均可略過。

另一個已回答的實作待驗證案例（[03 U06／J02](../../discuss/03-research-design/README.md)）：背景工作不得遺漏是已知要求；候選已有使用案例，但本 repo 部署方式下，服務重啟後是否仍不漏工作尚未驗證。使用者認為這需要實作才知道，不必在研究階段因此特別阻擋，可繼續設計討論。此案例仍是未驗證假設，不是降低既定要求、宣稱已驗證或自動授權實作；也不概括為所有未知均可略過。

對新增能力，使用者提出的保守方向是先提出需求；實際提供方式未定，授權與可提供能力分開判斷。依賴補裝的產品意圖及未決事項見 [configuration](configuration.md#任務期間的依賴與能力缺口)，不預設平台能啟用任何服務。

### 開發、review 與有限修正

本節為具體流程候選；任務交接與完成界線見 [Issue 任務單與程式完成](#issue-任務單與程式完成)，必須由另一個 agent review 與 PR 修改交付見[已確認要求](#code-工作的獨立-review)。

遠端固定 commit → 開發候選 → 普通程式驗證該候選 → fresh review → 達標候選或必要修正／人工決定。

第一個閉環可建議最多一輪外層修正，尚未採納為正式上限，也不限制 Codex 工作內的一般自我修正。只修原授權範圍內的問題；形成新候選後重新驗證與 review，仍有阻擋問題就交回人。

候選須保存可重建 Git 資料，例如 bundle，不只 commit 字串或不完整文字 diff。若已授權發布，同一 worker 可在收尾推候選並回報分支／PR，平台核對遠端版本；不強制獨立 publisher，也不宣稱可強隔離禁止提前 push。合併／部署不自動納入。

### 取消、中斷與認證失效

以下行為已確認，來源：[05-interaction-recovery](../../discuss/05-interaction-recovery/README.md) U15–U18：

| 情境 | 行為與分界 |
| --- | --- |
| 執行中想改需求 | 不介入當前執行，完成後再進行一輪修改；使用者認為即時介入的系統成本過高。不要求即時轉向或先排隊等自動處理。 |
| 使用者選擇立即終止 | 提供立即終止、拋棄當次 run 的能力，例如規模很大且已確定要改規格時，不必等原 run 完成。這不是將新規格注入原 run，也不等於刪除整個工作、既有交付或回滾外部操作。 |
| Workbench 意外重啟、工作未完成 | 恢復後自動接續，不需使用者再手動啟動。 |
| 意外中斷後進度遺失、無法接續 | 可自動從頭重跑，不需再等使用者批准；未指定重試次數，不等於無限重試。 |

主動終止並拋棄的 run 不套用意外中斷自動恢復。Clarification 正常等待與手動中斷的既有連續性限定仍見[上節](#clarification-的連續性)，不能因允許意外中斷後重跑，就把正常等待當作清理時機。

下列為實作候選與待查事項，並非使用者已指定的完整狀態機：保存終止要求、停止後續派發，由 runner 停止執行；遲到成果不得推進已終止的 run。停止一個 worker 不應停止其他工作。立即終止是產品要求，停止時限、停止機制與清理方式尚未驗證。

恢復時先核對 attempt、容器、成果與已知外部操作，仍在執行則觀察、已有成果則收取、需要恢復則依上述基準接續或重跑，是候選實作方向。05 U18 取代舊「不重跑整件工作救援未知狀態」作為概括禁令的解讀；允許進度遺失時重跑，不表示 Push／PR 等外部副作用可盲目重複。外部回應不明先查遠端、仍不明時如何處理，以及防重、重試額度與恢復資料責任仍待設計；不宣稱已實現原程序復活或完整環境自動修復。

認證失效的既有候選處理仍為保存成果、停止依賴該認證的新工作，待修復後再判斷接續，詳見[認證設計](authentication.md)；不將平台意外重啟的回答擴張成自動修復認證或新增能力的授權。

## 保存與清理

| 必須保留 | 可丟失／重建 |
| --- | --- |
| 目標、回答、授權、有效配置、attempt 身分 | 容器、原程序與未落盤進度 |
| 已交付報告、[研究接手內容](#研究交付或等待回答)、候選資料、驗證紀錄與 findings | 未保存編輯、暫存檔與可重建快取 |
| 已知外部操作、取消與錯誤觀測 | Test services 的暫時資料 |
| 更新後認證，存於獨立受限位置 | 一般 session 的重建為候選；clarification 正常等待受連續性需求約束 |

Clarification 的回合結束或等待回答不自行構成正常清理時機，依[連續性需求](#clarification-的連續性)保留原 session；具體資源保存方案未定。其他工作正常清理前確認成果完整、登記版本與雜湊，再移除 worker。必要摘要帶來源與證據引用，不建立另一套會漂移的全文知識庫。

以 [C 組](../experiments/c-handoffs.md)驗證結果與交接，以 [D 組](../experiments/d-runtime.md)驗證重複派發、等待、取消及環境；不把 fixture 通過當成真實交付驗收。
