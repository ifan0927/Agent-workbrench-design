# 正式設計方法與討論順序

狀態：設計方法與討論順序已由使用者確認並授權落檔；各項產品與技術決策依其主題文件的狀態判讀。整理日期：2026-09-11。

目前進入正式系統設計階段，以 A–E 實驗為證據，從使用情境逐步收斂工作狀態、元件責任、契約與實作順序。這次先落實方法與討論入口，尚未完成首版細節或技術選型，也不開始產品實作或追加模型實驗。

## 方法與界線

先描述使用者如何完成一件工作，再定義操作造成的狀態變化、資料責任與跨元件契約，最後確定技術及部署方式。步驟可以往返調整，不要求先消除所有未知或一次凍結全部設計。

沿用[產品範圍](../product.md)：平台提供清楚的目標、配置、邊界與驗收，保留 agent 在工作內探索、規劃與修正的自主性。設計不固定每一步解題路徑。先採輕量文件與必要圖表；自訂規格語言、知識圖譜、程式生成或多 agent 審議流程，待出現具體維護問題再評估。

使用情境同步釐清「人如何操作」與「agent 如何取得資訊、工作及交付」，將全局／專案／模式指引、skills、context 與外層流程的需求帶入各主題。這不是把使用者訪談變成技術選型或 prompt 全文定案；具體方案與驗證要求仍依所屬文件收斂。可採[分題短訪談](../../discuss/README.md)取得材料，不必在一個 session 完成大型訪談。

## 討論順序與產物

下列是設計順序，不是必須依序實作的功能清單。目前從第 1 步開始，第 2–5 步尚待展開；已確認的產品基準不重新視為未決。

| 步驟 | 要回答的問題 | 產物與主要維護位置 |
| --- | --- | --- |
| 1. 首版使用情境 | 使用者要完成什麼？提供什麼資訊？何時啟動、等待或接手？Agent 需要哪些背景與自主範圍？成果怎麼看？ | 訪談材料先存 [discuss](../../discuss/README.md)；統整後的首版範圍、情境操作表與必要畫面草圖回到 [product.md](../product.md)，工作行為及指引需求分別連到 workflow／configuration。 |
| 2. 工作模型與狀態 | 工作、需求版本、回答、attempt、候選的身分是什麼？操作後如何變化？哪些事不得發生？ | 核心名詞、狀態轉移、驗收情境及取消／恢復語意，維護於 [workflow.md](workflow.md)。 |
| 3. 元件與資料責任 | 誰決定下一步？誰執行與觀察？哪裡的資料是準據？何時保存及清理？ | 元件與部署邊界、責任表、資料權威及關鍵時序圖，維護於 [architecture.md](architecture.md)；配置及認證細節各回其主題。 |
| 4. 跨元件契約 | 輸入、結果、事件與錯誤如何交換？版本不符、重複請求或部分寫入如何處理？ | 按主題維護契約與欄位語意；細部設計需要時再加入 schema／API 定義，內容過長才拆檔並補索引。 |
| 5. 技術與實作切片 | 如何實作首個可用閉環？哪些能力須先補證據？怎樣驗收及交接？ | 技術決策、依賴順序、資源界限與有界實作切片；技術理由回 architecture，切片細節確定後再建立必要文件。 |

第 3–4 步特別檢查 checkpoint、執行紀錄與成果檔案之間的部分完成情境：其中一處已保存、另一處尚未完成時，恢復程序如何查核，不能以資料庫中的意圖推定外部操作已完成。

## 第一步的四條情境

四條情境用來檢查設計是否涵蓋原始需求，不是四個永久 agent 角色，也不代表一次實作全部分支。

| 情境 | 討論起點 | 需釐清的內容 |
| --- | --- | --- |
| 設定專案與共用能力 | 加入專案、選用共用約定／模式／skills、預覽並固定有效配置 | 哪些準備只做一次？哪些每次工作可調整？缺少配置或發現衝突時如何呈現？ |
| 研究或設計工作 | 提交目標、探索、必要提問、回答接續、交付報告 | 目標釐清與研究自主性、依據及接手內容已有 [workflow 基準](workflow.md#研究交付或等待回答)；成果表示與保存機制、是否需要額外 review 仍待設計；無 repo 入場沿用 product 的 onboarding 基準。 |
| 開發或修正工作 | 固定需求及 repo 版本、coding、驗證、fresh review、必要修正、交付與採納 | 開始工作的最低資訊、成果呈現、修正界限、採納與下一步授權的區別。 |
| 取消與中斷恢復 | 使用者取消、平台重啟、認證失效或 worker 消失 | 可以繼續觀察、收取或接續的條件；未知狀態、部分成果與紀錄缺口如何呈現。 |

每條情境先寫「使用者操作 → 系統反應 → 可見成果／接手點」，再檢查正常、等待與失敗分支。必要時用時序圖或畫面草圖澄清；詳細 API、DB schema 與畫面樣式留到行為清楚後。

## 讓 AI 可接手的四個約定

1. **決策狀態明確。** 區分已確認、建議、待驗證、已取代；來源事實另附證據與適用版本。實驗通過不自動代表產品採納。文件混合多種狀態時，對各項結論分別標示。
2. **名詞與責任一致。** 核心名詞以 workflow 為主，元件與資料權威以 architecture 為主。其餘連結引用，不另造同義狀態或全文副本。
3. **規則以情境表達。** 寫明前置狀態、收到的操作、預期結果與不得發生的事；實作時據此建立行為驗收，避免只測程式自身的寫法。
4. **實作切片可獨立接手。** 每個切片具備目標、範圍、必要文件、完成條件與未決事項；下一個 session 不必重讀整段對話，也不預讀全部 docs。

文件形式按內容選擇：產品意圖與取捨用 Markdown；狀態、權限及錯誤處理用表格與必要圖示；跨元件資料進入細部設計才寫 schema；驗收先描述情境，實作時轉成測試。避免維護多份表達同一規則的格式。

### 輕量記錄格式

在所屬主題直接使用下列欄位，不為每個決策或每輪討論建立新報告；簡單決策可以用一小段文字涵蓋。

| 類型 | 最少內容 |
| --- | --- |
| 重要決策 | 狀態、要解決的問題、選擇、理由與證據、接受的限制、需要重議的條件。 |
| 行為規則 | 前置狀態、操作／事件、預期結果、不得發生的事；必要時補驗收方式。 |
| 實作切片 | 目標、範圍與不含事項、必要文件、輸入與輸出契約、完成條件、依賴及未決事項。 |

例如取消規則的驗收情境可從「執行中收到取消，保存操作、停止後續派發、核對 worker、保留部分成果，遲到結果不得推進」展開。具體狀態名稱與產品容忍條件在 workflow 討論，不在本方法文件另訂一套規則。

## 實驗如何支持設計

已有證據依[實驗入口](../experiments/README.md)按需查閱；lab 保留實作版本、歷史結果與限制。正式設計引用證據，不能直接把 lab 腳本升格為產品實作。

剩餘未知只在會影響決策時安排有界驗證；提出實驗時說明「哪個決策需要答案、最小驗證方式、通過／不通過會如何改變設計」。實驗仍在 lab，模型用量依共通規則只記 token；本方法不新增執行授權。

目前需要帶入各主題的討論線索：

| 線索 | 設計處理位置與界線 |
| --- | --- |
| 真實登入／OAuth 刷新 | [認證](authentication.md)：影響認證方案定案；先定模組責任及失效處理，再以 [A 組](../../lab/A/RESULTS.md)尚缺的真實生命週期證據檢查具體實作。 |
| 取消時命令缺少終態 | [工作生命週期](workflow.md)：討論執行狀態、成果判定、紀錄完整性與人的決定分開表示。已確認停止且保留 partial 的缺口可作容忍提案；正常成功工作缺關鍵驗證證據不能套用。產品條件待討論，[E6 歷史結果](../../lab/E/RESULTS.md)仍為 inconclusive。 |
| 長駐平台與同時操作 | [架構](architecture.md)：選定寫入及執行模型後，針對回答／取消競態、重複請求、重啟與部分寫入設計驗收。 |
| 遠端 repo、研究交付及資源限制 | 按第 1 步首版情境收斂所需能力，再驗證遠端準備、非 coding 成果及實際負載；不將 E 的單一 repo 或小型並行結果推廣為全面通過。 |

完整推理觀測、跨主機 session 遷移與大型併發不成為目前設計的前置門檻。是否增加能力，依產品需求與具體問題決定。

## 討論與審查方式

每次聚焦一個情境或少量相依決策：先引用現行基準，提出具體操作範例與建議，再說明會改變使用體驗的取捨。已有答案不重複詢問；一般可逆的文件與技術整理依現行授權進行。重要產品取捨尚未決定時，明確保留候選，不讓推論變成已確認規則。

討論結果回寫所屬主題，並核對相關契約是否受影響。進入細部設計前，用正常、等待、取消及恢復情境走讀一次，檢查控制權是否重複、資料是否有兩個準據、未決事項是否被隱藏。這是內容審查，不增加固定的多角色批准流程。

### 分題訪談與跨 session 統整

依使用者要求，訪談切成小主題，每場只處理一個具體片段；共用規則、起始主題地圖與 [prompt](../../discuss/prompts.md) 集中於 [discuss](../../discuss/README.md)。題目地圖是可調整的訪談分工，不是首版功能清單或必須完成的固定關卡。每題紀錄維護於 `discuss/{topic}/README.md`，同題接續原檔，不要求使用者複製上一場對話。

訪談材料與正式設計分開：前者保存明確回答、未確認摘要、具體例子及跨題衝突；統整時才回寫所屬 product／configuration／workflow／architecture。已确认的使用者回答可成為設計輸入，但不等於技術方案或完整首版已批准。訪談者不自行改寫正式文件，也不追加模型實驗。

取得足以支撐一個設計切片的相關材料即可統整，不等全部訪談完成。統整保留候選及未決身分，並在來源主題記錄已處理版本、條目與目標段落，避免同一決策在 discuss 與 docs 維護兩份全文。各 session 的寫入範圍仍依當次明確授權。

## 設計完成與接手條件

一個設計切片足以交付實作，應能讓下一個 session 從文件回答：

- 要實作哪個使用情境，首版包含及排除什麼。
- 哪些行為已確認，哪些仍是建議或待驗證；未決事項影響哪部分。
- 核心名詞、狀態、責任、資料來源及跨元件契約是什麼。
- 回答、取消、重複操作、失敗與重啟後應如何處理。
- 哪些證據支持設計、接受什麼限制、如何驗收，以及先做哪個切片。

完成條件不要求所有未來功能、欄位或部署細節先定完。文件落檔檢查連結、狀態、術語、分類與完整變更；純文件變更通常不需要應用程式測試。

## 目前接續入口

**以分題短訪談接續第 1 步「首版使用情境與 agent 工作方式」，有足夠材料就統整，再銜接第 2 步工作狀態。** 訪談／統整啟動方式見 [discuss/prompts.md](../../discuss/prompts.md)。

已完成統整的 onboarding 基準見 [product.md](../product.md#專案入場與-onboarding)；02 的目標釐清與階段銜接見 [workflow](workflow.md#目標釐清與必要取捨)，索引自主性見 [configuration](configuration.md#索引與閱讀自主性)。03 的研究與設計成果方向見 [product](../product.md#研究與設計的成果方向)，是否研究、何時停止及接手內容見 [workflow](workflow.md#研究交付或等待回答)。不再從頭訪談這些已有答案。

下一個有價值的設計切片是 clarification 等待期間的 session／容器生命週期：依 [architecture 的待決接縫](architecture.md#clarification-帶來的待決接縫)比較保存、手動中斷與能力變更的責任及成本，再決定技術與必要驗證。此處只指定接續點，不自行啟動實作或實驗。

第一份討論產物是操作／agent 行為情境與需求分界，不先建立產品 repos 或完整 schema。訪談材料按固定結構存入 discuss；正式結論統整回既有主題。後續接手時先讀本節與指定主題，直接沿用已確認內容繼續討論。
